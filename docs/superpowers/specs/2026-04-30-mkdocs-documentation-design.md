# MkDocs Documentation — Design Spec

**Date:** 2026-04-30
**Status:** Approved (brainstorming phase)
**Owner:** ICIJ / Pierre Romera

## Problem

`kuroi` ships as a CLI for stripping sensitive data from PDFs with LLM
assistance, plus a small Python package that contributors and library
consumers will eventually want to import directly. There is no published
documentation today — only a one-line README and internal specs/plans
under `docs/superpowers/`. We need a single documentation site that:

1. On-ramps end users for the four primary CLI use cases.
2. Helps contributors hack on the codebase.
3. Gives library consumers a discoverable Python API reference.
4. Gives rule authors a reliable schema reference for YAML rule packs.

## Goals

- Publish a Material-themed MkDocs site at GitHub Pages with a
  consistent dark visual identity.
- Cover the four end-user use cases — quick start, batch redaction,
  switching LLM providers, audit/diff/undo/backups — with worked,
  runnable examples.
- Provide three developer entry points — contributing, library usage,
  rule authoring — alongside an architecture overview.
- Auto-generate the CLI reference (from Typer), the Python API
  reference (from docstrings via mkdocstrings), and the rule-pack
  schema reference (from the dataclasses in `core/rules.py`) so that
  reference content cannot drift from the code.
- Build cleanly under `mkdocs build --strict` in CI on every pull
  request.
- Deploy automatically to GitHub Pages on merge to `main`.

## Non-Goals

- No multi-version docs yet (`mike` is deferred until 1.0). A single
  `latest` channel tracks `main`.
- No PR previews (GitHub Pages does not natively offer them; Read the
  Docs was rejected to keep hosting in-house with the GitHub Action
  workflow).
- No light/dark theme toggle. The site is permanently dark.
- No translations / i18n.
- No analytics.
- No hand-written CLI/API reference pages — reference content is
  auto-generated; only short prose intros are hand-written.

## Audiences

| Audience              | Primary section          | Notes                                                         |
| --------------------- | ------------------------ | ------------------------------------------------------------- |
| End users (CLI)       | User Guide               | Cover all four use cases with examples.                       |
| Contributors          | Developer Guide          | Architecture, dev setup, tests, commit conventions.           |
| Library / API users   | Developer Guide + Reference/api | mkdocstrings reference + a "library-usage" how-to page. |
| Rule authors          | Developer Guide + Reference/rule-schema | Hand-written guide + auto-generated schema. |

## MkDocs Configuration

Top-level `mkdocs.yml` essentials:

- `site_name: "kuroi"`, `site_description`, `site_url` (set on first
  deploy), `repo_url: https://github.com/ICIJ/kuroi`,
  `repo_name: ICIJ/kuroi`, `edit_uri: edit/main/docs/`.
- `docs_dir: docs`.
- `exclude_docs: |` with `superpowers/` listed.
- Explicit `nav:` mirroring the IA above (no auto-nav).
- Markdown extensions: `admonition`, `attr_list`, `md_in_html`,
  `tables`, `pymdownx.details`, `pymdownx.superfences` (with a custom
  fence for mermaid), `pymdownx.tabbed` (`alternate_style: true`),
  `pymdownx.snippets` (base path `docs/_snippets`), `pymdownx.highlight`
  (line numbers + anchor links), `pymdownx.inlinehilite`,
  `pymdownx.keys`, `toc` (permalink).
- Plugins: `search`, `mkdocs-typer2`, `mkdocstrings[python]`,
  `mkdocs-gen-files`, `mkdocs-literate-nav`.

Pinned versions live in a new `[project.optional-dependencies].docs`
group:

## Theme & Visual Identity

Dark-only Material configuration:

```yaml
theme:
  name: material
  language: en
  palette:
    scheme: slate
    primary: black
    accent: red          # tuned in extra.css
  font:
    text: Inter
    code: JetBrains Mono
  logo: assets/logo.svg
  favicon: assets/favicon.svg
  features:
    - navigation.tabs
    - navigation.tabs.sticky
    - navigation.sections
    - navigation.indexes
    - navigation.top
    - navigation.footer
    - toc.follow
    - search.suggest
    - search.highlight
    - content.code.copy
    - content.code.annotate
    - content.tabs.link
extra_css:
  - stylesheets/extra.css
```

`docs/stylesheets/extra.css` overrides the `slate` scheme custom
properties:

- `--md-default-bg-color`: deep neutral (`#0f1115`), slightly above
  pure black for prose readability.
- `--md-default-fg-color`: high-contrast off-white.
- `--md-primary-fg-color` and header background: near-black.
- `--md-accent-fg-color`: ICIJ red. Exact hex tuned during
  implementation (target around `#d62828`); the design treats this as
  a one-line CSS change rather than a blocker.
- Code-block background lifted above page background so fenced blocks
  visually separate without a border.
- `--md-typeset-a-color` adjusted so dark-scheme links don't glow.

Mermaid diagrams are rendered with a dark theme so the architecture
diagram does not flash white.

Logo and favicon ship as placeholder wordmarks; the implementation
plan will note "TODO: replace with final ICIJ artwork" rather than
block on assets.

## Content Plan

### Home (`index.md`)

One-paragraph introduction to kuroi, a 30-second demo (static fenced
block; asciinema deferred), and a Material grid of three cards linking
to *Install*, *Quick start*, and *Library usage*.

### User Guide

- **install.md** — `pip install kuroi`, `uv tool install kuroi`,
  install from source, verifying with `kuroi doctor`. System
  requirements (Python 3.12+, optional Ollama for offline usage).
- **quickstart.md** — set `ANTHROPIC_API_KEY`, run
  `kuroi run document.pdf`, view the diff, accept/reject. End-to-end
  walkthrough using a real example PDF, with Rich-output screenshots.
- **batch.md** — globbing folders, output resolution rules
  (referencing `core/output_resolution.py`), interrupt/resume via
  state, parallelism flags, cost estimation via `core/pricing.py`,
  worked example over a 50-PDF folder.
- **providers.md** — provider table (Anthropic, Ollama), `kuroi
  models`, choosing models, env-var vs `kuroi config` precedence,
  fully-offline workflow with Ollama, switching providers mid-project.
- **audit-and-undo.md** — `kuroi diff`, `kuroi verify`, `kuroi
  backups list/gc`, `kuroi undo`, where audit logs live, how to read
  them.
- **troubleshooting.md** — common failures (missing key, locked file,
  provider rate limits, oversized PDFs), `kuroi doctor` diagnostics,
  log locations.

### Developer Guide

- **architecture.md** — module map (`cli` → `core` →
  `providers`/`rules`), data-flow mermaid diagram,
  state/locks/audit/backup roles, key invariants (idempotency, atomic
  writes).
- **contributing.md** — dev setup with `uv`, Makefile targets, running
  tests / lint / typecheck, commit conventions (Conventional
  Commits), running the docs locally with `make docs`.
- **library-usage.md** — using kuroi as a Python library: stable
  public API, minimal example
  (`from kuroi.core.redaction import redact_pdf`), error types, and
  what is *not* part of the public API.
- **adding-a-provider.md** — implement `providers/base.py`, register
  in `factory.py`, add pricing entry, write tests, add a docs entry.
  Worked example walking through the existing Ollama provider.
- **writing-rule-packs.md** — anatomy of `pii-en.yaml`, link to the
  auto-generated schema reference, regex vs LLM-assisted detection,
  validation, packaging your own rule pack, pointing kuroi at it via
  config.

### Reference (auto-generated, light prose intros)

- **cli/** — one page per Typer command (`run`, `diff`, `models`,
  `backups`, `config`, `doctor`, `setup`, `undo`, `verify`), generated
  by `mkdocs-typer2` from the live Typer app. Each page renders
  synopsis, options table, exit codes, and (for prose-heavy commands)
  two example invocations injected from `_snippets/`.
- **api/** — `mkdocstrings`-rendered modules: `kuroi.core.redaction`,
  `kuroi.core.findings`, `kuroi.core.rules`, `kuroi.providers.base`.
  Sticky table of contents per page.
- **rule-schema.md** — generated from the rule dataclasses via
  `mkdocs-gen-files`. Hand-written intro paragraph; generated body.
- **config.md** — config-key table sourced from `core/config.py`,
  env-var equivalents, precedence rules.
- **exit-codes.md** — short table of CLI exit codes.

### About

- **changelog.md** — included from a `CHANGELOG.md` file at repo root
  via `pymdownx.snippets` (single source of truth; the CHANGELOG file
  will be added in the implementation plan).
- **license.md** — AGPL-3.0-or-later notice and link.

### Cross-cutting conventions

- Every command and example is a real, runnable invocation. No
  `<TODO>` placeholders in shipping pages.
- Tabbed code blocks for `pip` / `uv tool` / `from source` install
  variants and for `Anthropic` / `Ollama` provider snippets.
- Admonitions: `!!! warning` for destructive commands (e.g., `backups
  gc`), `!!! tip` for productivity hints, `!!! danger` for
  AGPL/data-handling notes.
- Reusable fragments live under `docs/_snippets/`.
- No dead links: a reference page is added only when its target
  symbol exists.

## Automation & CI

### Local development

- New `[project.optional-dependencies].docs` group (see versions
  above).
- New Makefile targets:
  - `make docs` → `uv run mkdocs serve -a 127.0.0.1:8000` (live
    reload).
  - `make docs-build` → `uv run mkdocs build --strict` (fails on
    warnings).
- `make dev` updated to install the `docs` extra so contributors get
  one-shot setup.
- Workflow documented in `developer-guide/contributing.md`.

### CI: build check on every PR

A new `.github/workflows/docs.yml` (or a new job in the existing CI
workflow):

- Triggers: `pull_request` on any branch and `push` to `main`.
- Steps: checkout → setup Python 3.12 → `uv sync --extra docs` →
  `uv run mkdocs build --strict`.
- `--strict` is the safety net: any unresolved internal link, missing
  nav entry, or plugin warning fails the PR.
- Cache `~/.cache/uv` to keep the build fast.

### CD: deploy on merge to main

A second job in `docs.yml`, gated on
`github.ref == 'refs/heads/main'`:

- Uses `actions/checkout@v4` (`fetch-depth: 0`).
- Auth via the default `GITHUB_TOKEN` with permissions
  `contents: write`, `pages: write`, `id-token: write`.
- Build the site, then publish via the official
  `actions/upload-pages-artifact` + `actions/deploy-pages` flow. This
  is preferred over `mkdocs gh-deploy`: no `gh-pages` branch, plays
  cleanly with the "GitHub Actions" Pages source.
- `concurrency: { group: pages, cancel-in-progress: false }` so
  simultaneous merges do not stomp each other.
- One-time manual repo configuration: set Pages source to "GitHub
  Actions". Implementation plan will call this out.

### Code-to-docs sync guardrails

- Auto-generated CLI/API/rule-schema reference means a removed or
  renamed Typer command, public function, or rule field will fail
  `mkdocs build --strict`. This forces docs maintenance into the same
  PR as code changes.
- `mkdocstrings` configured with `docstring_style: google`. The
  implementation plan will include a one-pass docstring audit on the
  public surface to fill gaps before the API reference page goes
  live.
- `developer-guide/contributing.md` documents the auto-gen contract
  and points at where to edit hand-written prose.

## Risks & Mitigations

| Risk                                              | Mitigation                                                                 |
| ------------------------------------------------- | -------------------------------------------------------------------------- |
| Auto-gen tooling drift                            | Pin `mkdocs-typer2` and `mkdocstrings` versions in `pyproject.toml`.       |
| Slow CI from network / repeated installs          | Cache `~/.cache/uv` and the Python toolchain.                              |
| Docstring gaps on public API                      | Implementation plan includes a docstring audit pass before going live.    |
| Repo Pages settings forgotten on first deploy     | Spec and contributing docs both list the one-time manual setting.          |
| Logo/asset placeholders block first publish       | Ship with placeholder SVG wordmarks; treat final artwork as a follow-up.   |

## Acceptance Criteria

- `mkdocs build --strict` succeeds locally and in CI.
- `make docs` serves the site with live reload.
- Every page in the IA above is reachable from the top nav.
- All four user-guide use cases contain at least one runnable example.
- The CLI reference page count equals the number of registered Typer
  subcommands; the rule-schema page reflects the current dataclasses.
- Pushing to `main` deploys the site to GitHub Pages via the workflow
  (after the one-time Pages-source setting).
- `docs/superpowers/` is not present in the built site.
